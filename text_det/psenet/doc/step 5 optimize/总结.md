# LearnOCR / PSENet 代码审查与训练结果分析

这次上传的 `psenet(1).zip` 包含完整的 PSENet 教学实现，以及从 320 到 1280 共七种训练分辨率的实验记录。

先给出两个结论：

1. 代码整体设计合理，PSENet 的核心算法链路完整。 上次提出的公共 Letterbox 预处理和 Checkpoint 序列化问题已经修改，代码结构比之前更清晰。
2. 训练结果有了新的突破：当前最佳 F1 已经从 0.6167 提高到 0.6444。 最好的配置不再是 768 训练、1024 推理，而是 960 训练、1280 推理。

## 一、七组训练实验的结果

数据集：ICDAR2015 Test，500 张图片，2,077 个参与评估的文字实例。所有结果均采用项目自己的 IoU 匹配评估器。

从结果来看：

- 320、512、640 的训练分辨率明显偏小，容易损失小文字的空间细节。
- 768 到 960 的提升比较明显。
- 1024 和 1280 并没有继续稳定提高精度，说明训练尺寸并非越大越好。
- 960→1280 目前是最佳实验组合，但由于不同实验使用了多种推理尺寸，还不能据此认定 960 一定是最优训练分辨率。

与此前的 768→1024 相比，960→1280 的 F1 提高了 2.77 个百分点，其中 Precision 提高 1.06 个百分点，Recall 提高 4.28 个百分点。

这是有意义的实验进展：模型不仅减少了相对比例的错误，而且成功检测到更多文本。

当训练尺寸只有 320 时，一段原始高度为 12 像素的文字，缩小后只有约 3 像素。在 C2 特征图上甚至不足 1 像素。

同时，`kernel.py` 会对文字区域进行多次收缩。很小的文字可能无法生成有效的 K1 核心，因而被排除出训练监督。

因此，较低分辨率下召回率偏低，与 PSENet 的结构特点是吻合的。

### 2. 提高推理尺寸通常有效，但有收益上限

固定同一个 768 训练的模型：

1024 到 1536 已经基本没有收益。训练和推理分辨率过度不一致，并不一定有效。

960 模型的情况稍有不同：960 推理为 0.6058，1280 推理达到 0.6444，说明这组模型仍然受益于提高推理分辨率。

还有一个代码层面的小细节：你当前的 `min_area=30` 和 `min_kernel_area=5` 都是输入画布像素单位。提高推理尺寸时，面积阈值对应的原图实际面积也会变小。所以 F1 提升既可能来自更多文字细节，也可能部分来自小文字更容易通过面积过滤，不能把提升全部归因于网络分辨率。

### 3. 目前没有证据说明 1024、1280 训练发生了过拟合

它们的测试指标低于 960，只能说明在现有配置、训练次数和随机性的影响下，这两组实验表现不如 960。

要判断过拟合，必须检查 `history.csv` 中 Train Loss、Validation Loss 和 Pixel Dice 的逐 Epoch 曲线。

压缩包没有提供这些 CSV，所以不能仅根据最终 F1 就判断过拟合或训练不充分。

## 三、代码审查：还有哪些地方需要修改？

我重点检查了上次重构后的代码，结论如下。

### 已经完成的改进

| 文件              | 结果                                         |
| --------------- | ------------------------------------------ |
| `preprocess.py` | 公共 Letterbox、正反向坐标变换、归一化集中管理，设计合理          |
| `dataset.py`    | 保留 `letterbox_and_polygons` 作为便利函数，没有必要再删除 |
| `model.py`      | ResNet18 + FPN + 3 Kernel Head 实现正确        |
| `kernel.py`     | Polygon Shrink 和标签生成逻辑合理                   |
| `loss.py`       | Dice Loss、OHEM 和训练 Mask 处理正常               |
| `pse.py`        | 连通域种子、BFS 扩张、实例提取正常                        |
| `predict.py`    | 正确复用公共预处理                                  |
| `evaluate.py`   | 能输出逐图结果和整体 Micro F1                        |

所有 Python 文件均通过语法编译检查。

### 仍建议修改的四处问题

1\. `train.py` 恢复训练可能覆盖原来的数据划分

`train.py:188–189`

当前代码在加载 Checkpoint 前重新生成并写入 `split.json`。如果恢复训练时修改了 `--seed`，就可能将新的 Train/Val 划分与原模型混用。

建议：Resume 时读取已有划分并验证，而不是无条件重新生成。

2\. `--resume` 可能不会使用新设置的学习率

`train.py:204`

`optimizer.load_state_dict()` 会恢复旧学习率，覆盖新建优化器时使用的学习率。这不是当前实验结果错误，但以后调整学习率继续训练时可能产生误判。

同时，Checkpoint 已经修改为安全类型存储，恢复训练时可以考虑改用 `weights_only=True`。

3\. `evaluate.py` 的输出目录可能覆盖不同参数的实验

`evaluate.py:150–151`

路径包含 Checkpoint 目录名、Split、命令行 Size，却不包含 Threshold、Min Area 等参数。

如果同一输出目录下多次评估不同阈值，结果文件会被覆盖。建议将主要推理参数加入目录名或提供独立的 Run ID。

4\. 最佳模型依据 Validation Loss 保存，而不是检测 F1

`train.py:318–321`

这并不是 Bug，但 Validation Loss 最低的 Epoch 未必是检测 F1 最高的 Epoch。

教学项目可以继续保持这一设计，只要清楚两者的区别。如果需要进一步优化，可以每隔若干 Epoch 计算一次验证集检测 F1。

代码结构方面，我暂时不建议再增加大量抽象层，例如单独建立 Backbone Factory、Trainer Framework 或复杂配置系统。

`predict.py` 和 `evaluate.py` 确实还有少量推理逻辑重复，但代码比较短。当前首要目标是理解算法，不必为了消除所有重复而牺牲可读性。

## 四、实验设计还需要注意一个问题

目前你已经多次根据 Test 集结果选择训练尺寸和推理尺寸。

对于学习和探索，这完全可以接受。但从严格机器学习实验的角度，相当于 Test 集间接参与了参数选择。

因此，F1=0.6444 应当称为目前的探索性测试结果，而不是未经调参影响的独立最终测试成绩。

如果准备封版，我建议将实验配置统一到验证集做一次比较，确认 960→1280 在 Validation 集上也有较好表现。无需为了这个再重新训练七个模型。

我不建议继续进行更多大规模训练。你已经完成了从 320 到 1280 的分辨率实验，获得了比较清晰的规律；继续换 ResNet50、增加 Kernel 数量或复杂数据增强，对理解 PSENet 原理的帮助有限。

最终判断：PSENet 的算法实现已经达到教学项目可以封版的水平。 完成上面的几个小修复和实验总结后，我建议正式转向 DBNet。

届时可以沿用 `preprocess.py`，保留独立的 DBNet Model、Label Generation、Loss 和 Postprocess，这样既能复用公共代码，又能清楚比较两种文本检测算法的核心差异。

补充一点：如果要进一步判断 960、1024、1280 三组训练为什么结果不同，最有价值的材料是各自的 `history.csv`。目前无法从最终 F1 推断它们各自的收敛状态或最佳 Epoch。
